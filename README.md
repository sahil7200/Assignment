# Morrow Market

Morrow Market is an Expo React Native e-commerce assignment app for Android, iOS, and web. It uses DummyJSON for authentication and product data, SQLite for local app data, Zustand for shared state, and English/Arabic translations with light/dark themes.

## Requirements

- Node.js LTS and npm.
- Android Studio and an Android emulator for local Android simulator runs, or an Android device with Expo Go.
- macOS with Xcode for the iOS simulator, or an iOS device with Expo Go.
- A modern browser for web preview.
- Network access for DummyJSON. Previously cached products and locally stored cart/favourites remain available when the API cannot be reached.

## Setup and Run

Run these commands from the project root:

```powershell
npm install
npx expo start
```

Then scan the terminal QR code with Expo Go, or press `a` to open Android and `i` to open the iOS simulator. For web, run:

```powershell
npx expo start --web
```

The Expo Router entry point is `expo-router/entry` as configured in `package.json`.

The branded native splash screen is configured with the `expo-splash-screen` plugin. It uses separate light and dark Morrow Market logo assets and remains visible until the initial database/session hydration finishes. The web target shows the matching logo as its bootstrap screen. Expo Go may not reproduce the configured native splash exactly; verify the final appearance in an Android/iOS development or release build.

## Environment and Configuration

No `.env` file, API key, or secret is required. The API base URL is `https://dummyjson.com`, configured in `src/services/api.ts`.

`app.json` configures the app name, deep-link scheme, native Expo plugins, and Expo Router web response headers. `metro.config.js` registers `.wasm` as a Metro asset and sets the cross-origin isolation headers needed by Expo SQLite's web worker. If hosting the web export somewhere other than Expo's development server or Expo Hosting, configure the hosting server to return:

```text
Cross-Origin-Embedder-Policy: credentialless
Cross-Origin-Opener-Policy: same-origin
```

The `dist/` folder is generated by web export and should not be committed as source. Web session data is stored in browser `localStorage`; unlike native SecureStore, browser storage is not secure against script injection. Do not treat this demo storage as production-grade credential storage.

`App.tsx` and `index.ts` are files from the original blank Expo template. The configured app entry is Expo Router; routes are discovered from `app/`.

## API Mapping and Integration

All HTTP calls are centralized in `src/services/api.ts`. It uses `fetch` against DummyJSON and converts network/HTTP failures to `ApiError`. Screens and the store call the exported API functions rather than constructing requests in UI components.

| Feature | Request | Integration details |
| --- | --- | --- |
| Login | `POST /auth/login` | Sends username/password and requests a 30-minute access-token lifetime. Returns user and access/refresh tokens. |
| Current user | `GET /auth/me` | Sends `Authorization: Bearer <accessToken>` to validate a stored login session. |
| Refresh session | `POST /auth/refresh` | Sends the refresh token and requests replacement tokens. Used during startup/session validation when the access token is rejected. |
| Signup | `POST /users/add` | Sends the registration fields. DummyJSON simulates creation; it does not issue signup tokens or deliver an OTP. |
| Product pages | `GET /products?limit={limit}&skip={skip}` | Catalog loads ten products at a time and requests further pages as the list reaches its end. |
| Product search | `GET /products/search?q={query}&limit={limit}&skip={skip}` | Search input requests matching data from DummyJSON. |
| Categories | `GET /products/categories` | Supplies the category selector. |
| Products by category | `GET /products/category/{slug}?limit={limit}&skip={skip}` | Requests the selected category from DummyJSON. |
| Product sorting | `GET /products?sortBy={field}&order={asc\|desc}` | Price and rating sort parameters are sent to the product endpoint. |
| Product detail/reviews | `GET /products/{id}` | Supplies product data, images, stock, minimum order quantity, warranty, return policy, and reviews. |
| User sample carts | `GET /carts/user/{userId}` | Reads a sample remote cart when the cart view is focused. |
| Create cart | `POST /carts/add` | Best-effort remote cart operation from the cart action. |
| Update cart | `PUT /carts/{id}` | Best-effort remote quantity/removal synchronization when a remote cart ID is available. |
| Delete cart | `DELETE /carts/{id}` | Best-effort remote deletion when the last local cart line is removed. |
| OTP/TOTP | No remote OTP request in this demo | OTP is a local test flow because DummyJSON does not deliver email/SMS codes. The assignment's `/2fa` utility is not used by this mock verification. |

DummyJSON create/update/delete endpoints are simulated and do not persist data server-side. The local SQLite database is authoritative for the app's cart and favourites. API failures do not clear local data. Product list/detail data already fetched by the app can be cached and shown offline.

## Local Database

The app opens `morrow-market.db` through `src/db/database.ts`. That module creates the schema. `src/db/repository.ts` owns app-specific SQL queries and converts rows to typed models. Zustand actions call the repository; screens do not access SQLite directly.

| Table | Columns/model | Purpose |
| --- | --- | --- |
| `cart_items` | `product_id INTEGER PRIMARY KEY`, `product_json TEXT`, `quantity INTEGER CHECK(quantity > 0)` | One row per product in the local cart; product data is serialized as JSON and quantity is stored separately. |
| `favorites` | `product_id INTEGER PRIMARY KEY`, `product_json TEXT` | Saved product snapshots, available offline. |
| `cached_products` | `product_id INTEGER PRIMARY KEY`, `product_json TEXT`, `cached_at TEXT` | Previously fetched product data for offline catalog/detail fallback. |
| `preferences` | `key TEXT PRIMARY KEY`, `value TEXT` | Selected theme and language. |

Cart actions validate `minimumOrderQuantity` (default `1`) and stock before writing. Preference values are `light`/`dark` for theme and `en`/`ar` for language.

## Authentication and Session Handling

### Login session

1. The login screen validates that username and password have values.
2. `api.login()` sends `POST /auth/login`.
3. `useAppStore.login()` creates an `AuthSession`, stores it through `sessionStorage`, and updates Zustand.
4. The router replaces the auth route with the protected tab navigator.

### Restore and refresh

At startup, `app/_layout.tsx` initializes SQLite and calls `useAppStore.hydrate()`. Hydration loads theme, language, cart, favourites, and the saved session. For a DummyJSON login session, it calls `/auth/me`. If the access token is rejected, it calls `/auth/refresh`, validates the replacement access token with `/auth/me`, and stores the rotated tokens. A network failure preserves the saved session for offline use; a non-network refresh/auth failure clears it. The tabs layout also redirects to login if there is no session.

The refresh function is used in startup hydration and explicit session validation (including before remote cart work). The app does not currently have a universal request interceptor that refreshes tokens for every API call.

### OTP demo signup

Signup calls `/users/add`, then keeps the returned demo user and a five-minute expiry timestamp in memory. Enter **`123456`** before it expires to create a local demo session. Resend resets the timer; it does not send an email or SMS. Pending signup state is not persisted, so reloading the app before verification means signup must be restarted. DummyJSON does not issue auth tokens for this simulated signup, so that demo session is restored locally and has no access token to refresh.

### Storage by platform

| Platform | Session storage |
| --- | --- |
| iOS / Android | Expo SecureStore |
| Web | Browser `localStorage` |

Native token storage uses the platform secure-storage facility. Web `localStorage` is not equivalent to SecureStore and should not be used for sensitive production credentials.

Logout deletes the stored session and resets navigation to login. Cart/favourites are intentionally local user data and are not cleared by logout in this demo.

## Theme, Language, and Arabic RTL

### Theme

`src/theme/tokens.ts` defines the color tokens for light and dark modes. Components read the current theme from Zustand and apply these tokens to backgrounds, text, controls, product surfaces, status bar, and navigation. The settings screen changes the theme through `useAppStore.setTheme()`, which saves the preference to SQLite and updates shared state immediately. Hydration restores it at startup.

### Language and translations

`src/i18n/index.ts` defines English (`en`) and Arabic (`ar`) resources and initializes i18next with `react-i18next`. User-facing labels should be added to both dictionaries and read in screens with `useTranslation()` and `t('translationKey')`. The selected language is stored in the `preferences` table and restored during startup.

### Arabic RTL

When Arabic is selected, the app sets `I18nManager.allowRTL(true)` and `I18nManager.forceRTL(true)`. The settings flow reloads the app so React Native can apply native RTL direction to navigation and layout. Shared screen/input/search components also apply language-aware `direction`, text alignment, and row direction. Switching back to English disables forced RTL and reloads in the same way.

## Validation Commands

```powershell
npm run typecheck
npx expo install --check
npx expo export --platform web
```

`npm run typecheck` checks the TypeScript source. `expo install --check` verifies Expo SDK package compatibility. The web export verifies Metro's `.wasm` handling and emits the app to `dist/`.
